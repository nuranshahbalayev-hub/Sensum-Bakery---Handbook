# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Sensum & Bakery — a single-page bilingual (RU/AZ) PWA barista handbook: drink recipes, prep ("заготовки") recipes, the "Витрина" (salads, sandwiches, desserts with allergen notes), promos ("Акции"), favorites (inside «Ещё»), a training tab («Обучение»: lessons and flashcards, quizzes generated from the recipe data plus a stored theory question bank, a game with ranks and owls, with results sent to the training manager's Google Sheet and Telegram). No framework, no build step — the entire app is one static `index.html` file (~580KB on disk, ~160KB gzipped: markup, CSS, JS and all data, of which the lessons are ~60KB and the theory bank ~25KB) plus photos in `images/`, a service worker, manifest, and icons. As of v1.112: 56 drinks, 23 preps, 35 vitrina items, 4 promos, 46 lessons, 129 theory questions, 82 photos. If the file keeps growing (more lessons), move the lessons out of `index.html` into a separate file the service worker caches; nothing is split yet.

## Commands

There is no build step — it's plain HTML/CSS/JS. The checks use stdlib Python and Node; the browser smoke test also needs Playwright and Chromium (installed by GitHub Actions):

```bash
python3 tools/audit.py          # recipe data, photos, versions
node tools/apps-script/test.js  # the Google Apps Script, against mocks
node tools/sw-test.js           # cache/network and offline recovery
node tools/training-test.js     # sync races, status thresholds, reward retries
node tools/smoke.js             # the whole app in headless Chromium at phone width
```

The smoke test serves the repo root locally and clicks through every tab and sub-screen, a card, the AZ switch, the quiz generators (it recomputes the truth of every generated recipe, vitrina and exam-style question from the recipes, in both languages), the employee login, full tests, the weekly limit, practice tests, lessons, the training plan, the game and the style guide (~180 checks). Requests to `script.google.com` are answered by an in-page mock (code `1234` is the known employee), so it never writes to the real results sheet or sends a Telegram message.

The data audit:

It reads `DATA` / `IMAGES` / `CHANGELOG` out of `index.html` and checks (photo files exist and their filename hash matches the content, leftover files in `images/` are reported): RU/AZ parity (same ids, same `ing`/`steps`/`usedin`/`anote` lengths, same `cat`/`img`/`alg` and vitrina facts), every `cat`/`kind`/allergen key exists in its dictionary and in `ALG_ORDER`, vitrina facts are well-formed, every `img` exists in `IMAGES`, every prep `trig` actually occurs in the ingredients of the items in its `usedin` (both languages), promo, changelog and `SPOTLIGHT` ids resolve (spotlight dates well-formed), and `APP_VERSION` matches `sw.js` `CACHE`; `Code.gs` `LESSON_TOTALS` equals the number of lessons per id prefix. It also checks the design-system rule of the stylesheet (`check_css`: no colour literal outside the `:root` token blocks, no undefined `var()`, no colour in an inline style, no px font-size outside the fixed-glyph list `FIXED_FS`, no literal duration in a transition or animation). Exit code 1 means a real problem (**run it before every push that touches `index.html`**); `WARN` lines are advisory (e.g. vitrina items without a photo fall back to an icon, and promo gift-drink choices are plain names, not ids). To preview locally:

```bash
python3 -m http.server 8000
```

then open `http://localhost:8000/index.html`.

Deploying is `git push` to `main` — GitHub Pages (legacy build, serving the repo root of `main`) rebuilds automatically in about a minute. Live at https://nuranshahbalayev-hub.github.io/Sensum-Bakery---Handbook/.

Pushes go to a feature branch and are merged to `main` by the owner (pull request). **Open every PR against `main`**: a PR stacked on another feature branch merges into that branch and never reaches the site (merged branches are deleted automatically). **Before every push that changes `index.html`, run `python3 tools/release.py`**: it bumps `APP_VERSION` in `index.html` and `CACHE` in `sw.js` together (1.79 → 1.80; pass an explicit version to set one) and then runs the audit. This is an installed PWA; without the version bump, already-open/installed clients can keep serving stale content — see Service worker below.

## Architecture

### Data is embedded, not fetched

`index.html`'s main `<script>` opens with two single-line literals:

- `IMAGES` — `{key: "images/<key>.<hash>.webp"}` map; `img(key)` returns the path and every render site uses it as `<img src>`. Photos are separate WebP files in `images/`, **not** embedded. The 8-hex-char hash in the filename is the SHA-1 of the file content: because the service worker serves photos cache-first, a swapped photo must get a new URL or installed apps would keep showing the old one.
- `DATA` — every list/dictionary exists as an `_ru` / `_az` pair: `drinks`, `preps`, `vitrina`, `promos` (lists) and `CATS`, `KINDS`, `VCATS` (vitrina categories), `ALG` (allergen names) (dictionaries). `ui` is the single RU/AZ string table read through `T(key)`.
  - Vitrina items: `{id, name, cat, img?, desc, alg:{has:[…], may:[…]}, anote, tags, wt?, stor?, life?, kcal?, nut?}`. Allergens are derived from the composition; `anote` is the free-text caution (e.g. sauce usually contains X). `img` is optional — cards fall back to `VIT_ICON[id]` / `VIT_CAT_ICON[cat]`. The optional facts come from the owner's menu sheet (food_book.xlsx) and are language-neutral, identical in `_ru` and `_az`: `wt` weight in grams, `stor` `[min, max]` storage °C, `life` `[n, 'h'|'d']` shelf life, `kcal` and `nut` `[protein, fat, carbs]` grams, both per 100 g; `openVit()` renders them (`vitFacts()` / `vitNut()`). A new allergen key goes into `ALG_ru`, `ALG_az` and the `ALG_ORDER` list in the code.
  - Promos: `{id, icon, name, sub, price, days[0–6], from, to, parts:[{title, ids, extra}], notes?, branches?, …}`; `promoStatus()` decides whether a promo is active now (by day and time only: the app doesn't know which branch it is in). `branches` is the text of a branch restriction, shown with 📍 on the promo card and in its sheet. The promo row is ordered by `promosSorted()`: active now first, then the ones starting later today (soonest first), then ended or not running today; `tickPromos()` re-renders the row when that order changes.
  - Lessons (`lessons_ru`/`lessons_az`: `{id, cat, topic, title, blocks}`, `lcats_*`: `{CF:{ic,t,d}}`): the written lessons of «Материалы», **imported** from `tools/lessons.json` by `tools/lessons.py`, checked by `audit.py` (`check_lessons`). Blocks are `{h}` `{p}` `{note}` `{ul}` `{ol}` (item = text or `{b, t}` bold lead + rest) `{table:{head, rows}}`; they are rendered with `esc()`, never as markup.
  - Theory (`theory_ru`/`theory_az` questions, `tdirs_*` directions, `ttopics_*` topics): the question bank of the «Теория» section, see Training. Unlike the lists above these are **imported**, not hand-edited: `tools/theory.py` writes them from the trainer's Google Sheet, and `audit.py` checks them.
- `SPOTLIGHT` (a code constant above the promotions code, not in `DATA`) — the «Новинка» banner pinned above the «Напитки» list: `[{id, start, end}]`, local dates `YYYY-MM-DD`. `renderSpot()` shows the first entry whose `end` hasn't passed (also before `start`, so staff can learn the recipe early: the status reads «Старт продаж: 1 ноября», then «В продаже с 1 ноября»), hides it while searching or when the filters exclude the drink, every block marked `.topblock` above the cards of a tab (the promos `#promos-drinks` / `#promos-vit`, the banner `#spot-drinks`; «Заготовки» has none today) hides while a search is typed in that tab (`syncTop()`, called by `renderDrinks()`, `renderPreps()` and `renderVit()`; the chips do not hide them): **mark any new notice above the cards with `class="topblock"`**, and `openDrink()` adds a «Старт продаж» chip. Name, photo and the first four ingredients come from the drink itself, so a new spotlight needs no new texts. To feature another drink, replace the entry; an empty array turns the banner off.

`DATA` is compact JSON on a single very long line (~150KB). Don't `grep`/`Read` that line directly. Extract it with a small Python script (find the `DATA={` offset, bracket-match to the closing `}`, `json.loads` — `tools/audit.py` has an `extract()` helper) when you need to inspect entries, and do targeted string replacement in `index.html` for edits rather than round-tripping the whole blob.

`APP_VERSION` and `CHANGELOG` (array of `{id, date, type: 'news'|'fix', title:{ru,az}, items:{ru,az}, changed:[ids]}`) live right after `DATA`. The «Изменения» screen (under the «Ещё» tab) renders `CHANGELOG` directly, in array order (newest first by default; the owner may pin an entry to the top, e.g. Lotus Latte). That order also drives unseen tracking: `sensum_seen_change` stores the id of the first entry, and everything above the stored id counts as unseen, so moving an older entry to the top re-marks it unseen for clients who had already seen past it. Other persisted client state (`localStorage`): `sensum_lang`, `sensum_theme`, `sensum_favs` / `sensum_favpreps` / `sensum_favvit` (favorites per section), `sensum_learn` and `sensum_learn_u_<code>` (training: see below). Unseen changelog entries (tracked via `localStorage.sensum_seen_change`) populate two separate sets that drive card badges: `type:'fix'` → `changedSet` → `T('lbl_updated')` "Обновлено"/"Yeniləndi" badge; `type:'news'` → `newSet` → "Новинка"/"Yeni" badge (checked first, so a brand-new item shows "Новинка" rather than "Обновлено" even though both types can carry a `changed` list).

### Search

`drinkMatch()`, `prepMatch()` and `vitMatch()` use `found(query, text)`: both sides go through `fold()` (lower case, accents and marks removed, so `İ`/`ı`, `é`, `ё`/`й` compare as plain letters), and **every word** of the query must occur somewhere in the text (name, category, ingredient names; preps also the drinks they are used in; vitrina also the composition and tags). The Latin names also answer to their usual Russian spellings: `aka(name)` adds the words of `ALIAS` (a code constant, search only, never shown) for each Latin word of the name, so «капучино», «флэт уайт», «раф ваниль» find their cards. A new Latin word in a name that staff would type in Cyrillic gets an `ALIAS` entry. `setLang()` also sets `<html lang>`, so screen readers use the right voice.

### Clickable prep links (`trig`)

Every drink/prep ingredient name is plain text in its `ing` array, e.g. `["Сироп корицы","20 мл"]`. `ingRows(list)` makes an ingredient clickable by calling `prepFor(name)`, which does a case-insensitive substring match: for each prep `p`, if `name.toLowerCase().includes(p.trig)`, the ingredient links to `p.id`.

**Convention:** a prep's `trig` is a lowercase part of its own `name` (usually the whole name; shorter where the name carries a suffix the ingredient text doesn't, e.g. "Сироп Blue Tea" → `blue tea`), and it must actually occur as a substring inside the ingredient text used by every drink/prep listed in that prep's own `usedin` array — in both RU and AZ. `trig: "§нет§"` means the prep is never auto-linked. If an ingredient gets renamed (e.g. "Коричный сироп" → "Сироп корицы") without updating every reference, or `trig` carries extra text the real ingredient string doesn't have (e.g. AZ `"mix rum (premiks)"` when the ingredient says just `"Mix Rum"`), the link silently stops working — no error, the ingredient just renders as inert text. When renaming an ingredient or a prep, grep every `ing`/`usedin` occurrence of the old string across both languages, not just the prep's own `name`/`trig`. A full-app audit script (cross-referencing every prep's `usedin` list against the actual `ing` text of the drinks/preps it names) is the fast way to check for drift after a rename.

### Changelog entries vs. silent edits

Not every change gets a `CHANGELOG` entry. The standing rule from the project owner (Nuran): a genuinely **new** drink or prep gets a `type:'news'` entry (with `changed` listing its id, so it carries the "Новинка" badge); a **significant change in technique** that staff need to notice gets a `type:'fix'` entry. Routine corrections — gram/quantity tweaks, an ingredient rename, a clarified step, a photo swap, a shelf-life change — do **not** get a changelog entry; just edit the data in place. If a request to change a drink/prep doesn't say one way or the other, ask rather than defaulting to logging it — unprompted "Обновлено" badges on cards nobody actually needs to re-read trains staff to ignore the tab.

### Language switching swaps whole arrays, not per-string

`LANG` (`'ru'|'az'`) selects `drinks`, `preps`, `CATS`, `KINDS` by re-pointing them at `DATA['drinks_'+LANG]` etc. (`setLang()`), then calls `_reindex()` to rebuild the `drinkById`/`prepById` lookup maps and `applyUI()` to re-render chrome text via `T()`. There's no per-component i18n — adding a language means adding matching `_az`-suffixed siblings for every top-level `DATA` key, plus every key in `ui`.

Azerbaijani has dotted İ/i vs dotless I/ı, which native `.toUpperCase()` / CSS `text-transform:uppercase` get wrong. Any UI text that needs uppercase display goes through the `upperLocale()` helper instead — don't reach for `text-transform:uppercase` on new AZ-visible text. (Since v1.116 the badges are in sentence case and need neither.)

### The card detail view is a bottom sheet, not a route

`openDrink(id)` / `openPrep(id)` / `openVit(id)` / `openPromo(id)` (the first three dispatched via `openItem(id)`) build the detail markup into `#sheetInner` and call `showOverlay()`. Every way of closing ends in `hideOverlay()`: the ✕ button and a backdrop tap (`data-close` / `#overlay` in the body click handler), Escape, and swipe-down. Route any new way of closing the sheet through `hideOverlay()` so the scroll unlock stays in sync.

**The system «back»** (Android button or gesture, Safari's swipe; since v1.124) does what the app's own ‹ would: `syncTrap()` keeps exactly one extra history entry (`{sensum:1}`) while there is something to go back from (`backable()`: the photo viewer, the sheet, or a visible `curBack()` button), and `popstate` closes the photo, then the sheet, else clicks `curBack()` (a running test asks through `quizGuard()`, and cancelling keeps the entry). At a tab's top level there is no entry, so «back» leaves the app as usual. `syncTrap()` runs from `showOverlay()`, `hideOverlay()`, `openPhoto()`/`closePhoto()`, `switchTab()` and `renderLearn()`; a new overlay or screen with a back button needs the same call.

Swipe-to-dismiss is the pointer-event IIFE after `switchTab()` (`onDown` / `onMove` / `onUp`): any downward drag starting anywhere on the sheet is claimed at once (`preventDefault`, so iOS rubber-banding never takes over), arms after 8px, and closes past `min(140px, 28% of the sheet)`; shorter drags spring back. Page scroll lives only in `#scrollArea` (`html`/`body` are `overflow:hidden`), so `lockBodyScroll()` / `unlockBodyScroll()` just toggle `overflow` and `touch-action` on `#scrollArea`; its `scrollTop` is preserved while locked.

### The tab bar, «Ещё» and its sub-screens

The tabs are `drinks · preps · vitrina · learn · more` (since v1.105 «Обучение» is a tab of its own, in place of «Избранное», by the owner's decision). `switchTab()` knows seven views (`VIEWS`): the five tabs plus `changes` and `fav`, which `NAV_OF` maps to the `more` button so it stays highlighted while a sub-screen is open. The hub (`renderMore()`) shows one tile per sub-screen («Изменения», «Избранное» with the number saved, the text size); each sub-screen has a `.subbar` with a back button (`data-gotab="more"`). The unseen-changes dot (`#changesdot`) sits on the «Ещё» button; the training dot (`#learndot`, `updLearnDot()`) on «Обучение» when a logged-in person has done nothing of today's plan. Tapping «Обучение» while already in it goes back to its first screen.

### Training (Обучение)

- **Questions are generated, not stored.** `buildQuiz(items, scope, n)` takes the items of one part (`trainable(drinks)`, `trainable(preps)`, `vit`; items without `ing` are skipped) and `composeQuestions()` puts the parts together and calls the generators in `GEN`: `dose`, `comp`, `photo`, `vessel` for drinks, plus the exam-style questions across recipes (`has`, `without`, `both`, `most`/`least`, `same`, see below); `dose`, `comp`, `shelf`, `used`, `storage` for preps. A recipe edit changes the questions automatically; there is no question bank to maintain.
- **The vitrina is tested too** (`GEN.vcomp/vhas/vnot/valg/vstor/vlife`, scope `vitrina`, weights composition 8 : allergens 3 : storage and shelf life 2): the composition comes from `desc` (`vSplit()` splits on commas outside brackets, `vIngs()` gives the top-level ingredients), «семья» of an ingredient is the same first word (`vMentions()`, which also looks inside brackets), allergens are checked by family (`nuts_almond` ~ `nuts`) against both `has` and `may`, and the wrong storage and shelf-life options come from fixed pools (`V_STOR`, `V_LIFE`) that do not touch the right value, because most dishes share 2–5 °C and 24 h. Every question has exactly one right option, `smoke.js` recomputes all of them in both languages. `mkQ()` marks `isVit`, `itemById(id,isPrep,isVit)` resolves it, and the card box is `v:<id>`. The vitrina is two questions of the general test of the week (and four of the exam); the decks of the vitrina cards end with a practice test.
- **Distractor rules to keep when touching the generators:** dose distractors prefer real doses of the same ingredient elsewhere, then rounded multiples (`niceNum`); `comp` never offers an ingredient whose first word matches one of the item's own; `photo` never offers a drink showing the identical picture, compared by the content hash in the file name (`imgHash()`), since the Raf drinks have separate keys and file names for one photo; `used` never offers a drink that mentions the prep in its ingredients, even if `usedin` forgot it. Doses parse only `N г|мл|шт|q|ml|əd` (`QRX`); decor lines (`декор`/`dekor`) are skipped.
- **Exam-style questions across recipes** (the written Foundation exam asks these; `genHas`, `genWithout`, `genBoth`, `genMost`, `genSame`): «в каком напитке используется X», «какой напиток НЕ содержит X», «какой содержит и X, и Y», «у какого из этих напитков больше/меньше всего X», «в каком напитке X столько же, сколько в Y». The subject drink `x` is always the right answer, and **every wrong option is checked against the recipes, so exactly one option is right** (the exam's own versions of these had two right answers more than once). Rules to keep: a wrong option never has the ingredient *or its family* (`dMentions`: same name, one inside the other, or the same first word, so single and double espresso count as one family); `most`/`least` compare only the four shown options and need a real difference (≥10 % of the larger amount, so 210 against 220 ml is never asked), and ties among the wrong options are fine; `without` takes an ingredient that at least two drinks of x's own category use; `both` offers only drinks that have exactly one of the two. They explain themselves after the answer (who has what, with amounts). Only the drinks test gets them: `buildQuiz(..., extra=false)` keeps the drinks part of **«Экзамен месяца»** on the plain set, because it feeds the KPI. (The exam's composition changed in v1.103 from 12 drinks + 8 preps to the mix above, so its scores are not comparable with earlier months.) `smoke.js` recomputes the truth of every generated question from the recipes in both languages.
- **Progress is kept per person** (`USER_FIELDS`, including `progChanges`, `progV` and `progRemoteTs`): it lives under `sensum_learn_u_<code>` (`_guest` without a login), while `sensum_learn` keeps the device's `me`, `outbox` and `live`. `switchUser(me|null)` saves one person's bucket and loads the other. Since app v1.107 / script v5.7, call `touchProgress(k)` after changing a card box, and `touchProgress()` after marking a lesson. Protocol 2 sends only `{changes:{key:{v,ts}}, read, ts}`; explicit zero resets and per-card timestamps prevent a stale device from replacing unrelated cards. `applyProgress()` merges remote cards around pending local edits and ignores older server snapshots. A sync acknowledgement removes only the exact edits sent, preserving edits made while the request was in flight. `me.progressProtocol===2` is required before uploading; until the server is updated, local progress stays pending. Old local snapshots with a known baseline migrate only changed cards; with no baseline they only fill missing server cards. History and today's plan remain local.
- **Resetting every phone (end of a test period).** `RESET_EPOCH` (index.html, next to `LS`) is stored as `sensum_learn.epoch`. When a phone starts with a different number, it deletes all `sensum_learn_u_*` buckets (guest too), empties `outbox` and `live`, keeps `me`, and stores the number — once. So: clear the sheet's «Результаты» (A:G and J:R; **leave the formulas in H:I only if rows stay, otherwise clear them too, the script writes them with each row**), «Совы» A2:I and «Прогресс» A2:F by hand, raise `RESET_EPOCH` by one, release. Phones still on the old version can push old data again until they update; clear the sheet again after the release has reached them. v1.104 set it to 1 (end of the first test period, 02.11.2026).
- **Flashcards** keep a Leitner box per item in `LS.box` (keys `d:<id>` drinks, `p:<id>` preps, `v:<id>` vitrina, `t:<id>` theory questions): «Знаю» +1 (max 5), «Повторить» resets to 0 and re-queues the card once. An item counts as learned at box ≥ 2, and a wrong quiz answer resets its box to 0.
- **Theory (Теория)** is no longer a scope of its own: since v1.112 three of the ten questions of the weekly general test (and six of the exam) are theory, from the open topics. Unlike recipe questions these are **stored**: the trainer keeps a question bank in the Google Sheet «Sensum Обучение: банк вопросов» (folder «Sensum Обучение» on Google Drive; tabs «Темы», «Вопросы», «Замечания»). A question reaches the app only with the status «Утверждено»; the AZ text of the new questions is a draft until a native speaker has checked it. To update: export `'Вопросы'!A1:T…` and `'Темы'!A1:E…` as the Sheets connector's JSON, run `python3 tools/theory.py questions.json topics.json`, then `tools/release.py`. Question shape `{id, topic, lvl, type, q, opts, ans}`; `id` is the sheet's id (`CF-07`), `topic` a code like `CF-7` whose letters before the dash are the direction (`CF` coffee, `SV` service and sales, `SN` sanitation, `BR` brand; names in `TDIRS` / `TTOPICS`), `lvl` is `trainee|barista|senior` (see Levels below). The levels were set by one criterion, «what a person must know at that stage» (trainee: guests, sales basics, hygiene, who we are, simple facts about coffee and milk; barista: how coffee is made and why, sales psychology, the company's directions; senior: numbers and analysis, SCA norms, strategy); the sheet's «Как пользоваться» tab says the same. `type`: `one` (`ans` = index), `multi` (sorted indexes), `order` (indexes in the right order), `num` (`ans` = the number, no `opts`). ### Training results: Google Sheet, Apps Script, Telegram

- `RESULTS_URL` (top of the training code) is the `/exec` URL of the Apps Script web app bound to the sheet «Sensum Обучение: результаты тестов» in the owner's Google Drive (folder «Sensum Обучение»). An empty string turns sending off, and tests then run without an employee code.

- A finished quiz goes into `sensum_learn.outbox`; `flushOutbox()` POSTs it as `text/plain` JSON (`{id, code, scope, kind, score, total, mistakes:[{q,a,c}], lang, ver, ts, secs, timeouts, away, aborted}`). `text/plain` avoids a CORS preflight. API requests use `cache:'no-store'` and are outside the service worker's asset allowlist. Offline results stay queued. `api()` gives up after `API_WAIT` (20 s for a GET, 45 s for a POST, through an `AbortController`) and rejects with `e.timeout`, or `e.server` when the answer is not JSON (a Google error page), else it is a network error; the login says which (`id_timeout`, `id_server`, `id_offline`) and ignores a second tap while it waits (`loginBusy`). A repeated ID does not append a result or send another notification, but retries reward processing and returns the award linked to that attempt. `{error:'reward_pending',saved:true}` keeps the saved attempt queued, shows that its reward is pending, and retries with backoff (15 seconds up to 2 minutes while visible), plus the existing online/visibility retries. `unknown_code` logs that employee out but **keeps** the item, marked `rejected` (since v1.124; before, it was deleted): `flushOutbox()` skips it until someone logs in with that code again (the login clears the mark), and the result screen says so (`send_rejected`).

- The script appends the row to «Результаты» (A–M: the result, per-row formulas for % and pass/fail against the named range `PassThreshold`, the attempt id in M; N–Q since script v4: test time m:ss, «время вышло», exits from the app, «прерван» — an aborted test never passes; R since v5: the test type; `ensureHeaders_()` adds missing headers to an older sheet), sends a Telegram message at once when the score is below the threshold (for every test while «Уведомлять о каждом тесте» / `NotifyAll` is ticked, and always when the app was left during a question), a 24-hour digest daily at `DigestHour`, and on Mondays at `WeeklyHour` a weekly report including who hasn't taken a test in 7 days.

Eligibility, dedupe keys, monthly cap and award writes share one script lock. A partial write can be completed by retrying the same saved attempt without resetting credited checkboxes. Old eight-column rows remain valid. The Monday report lists outstanding credits; the trainer still marks actual transfers. Weekly streaks now require three qualifying tests in each counted week, matching the existing weekly reward; existing owl amounts are not recalculated. `me.passThreshold` supplies the test pass threshold for both result feedback and today's plan. Completing a failed test is labelled as completed/needs review, never passed.
- **«Вопрос дня» and «Сложные вопросы» (since v5.6):** a POST with `kind:'daily'` goes to `saveDaily_()` and its own sheet «Вопрос дня» (date, code, name, branch, right, questions, mistakes, id, aborted), **not** to «Результаты», so it never touches the summary, the KPI, the weekly limit, the instant messages or the study week. XP: 10 per right answer + 20 for all right (`DAILY_XP`), only for the first of a person's day (`dailyXp_()`), none if aborted; an owl only for 7 days in a row (v5.8). `me_()` adds its XP to `xp`, `weekXp` and the board, and returns `daily: {done, streak}` (`dayStreak_()`, Baku days). Every Monday `weeklyReport()` rebuilds the sheet «Сложные вопросы» (`rebuildHard_()`: question, mistakes, people, branches, section, right answer; 7 days, top `HARD_TOP`, tests and «Вопрос дня», the trainer's test account left out; RU and AZ wording count apart) and lists the repeated ones in the report; the menu «Sensum» → «Обновить «Сложные вопросы»» (`hardQuestions()`) rebuilds it at once.
- **Employee names and codes never go into this repo or `index.html`**: the repo and the GitHub Pages site are public. They live only in the private sheet.
- **Changing the script:** edit `tools/apps-script/Code.gs` and run `node tools/apps-script/test.js`; the owner then pastes it into the sheet's Apps Script editor and publishes it with **Deploy → Manage deployments → edit (pencil) → Version: New version → Deploy**. That keeps the same `/exec` URL; «New deployment» would create a new URL, and `RESULTS_URL` would have to change with it. **Every time a script has to be pasted, hand the owner, in the same message: (1) a link to `Code.gs` pinned to the commit SHA (`https://github.com/<owner>/<repo>/blob/<sha>/tools/apps-script/Code.gs`, plus the `raw.githubusercontent.com` one; not the branch name, a merged branch is deleted and the link dies), (2) the link to the results sheet, (3) the exact Deploy steps, (4) what `?action=status` should answer afterwards. The file is too big for the chat, so the links with «Copy raw file» are the delivery. The owner has asked for this every time.**

### Service worker

`sw.js` only intercepts GET requests for the explicit app-shell paths and hashed photos on this origin, without query strings. API calls and all other URLs go directly to the network; the client also requests API data with `cache: 'no-store'`. Within that allowlist the worker is network-first for documents (online fresh HTML, offline cached HTML) and cache-first for the other assets. Photos live in `sensum-img`, which survives a `CACHE` bump: installation reads the current image paths from `index.html`, downloads missing photos and removes obsolete ones. Activation clears older shell caches, including API responses cached by previous workers. Registration does not reload an already-open document on `controllerchange`; after deployment, close and reopen the installed app or reload the page to load the new frontend.

### Design system (UI)

The app's look is **design system v2** («тёплый Apple»: warm grouped backgrounds, one caramel accent, no borders or gradients on surfaces, depth by background, iOS text styles, line icons). It was designed in `design/concept.html` (approved by the owner 05.11.2026) and moved in five stages, one PR each, finished in **v1.117**; a sixth PR (**v1.120**, «полировка») made the remaining text follow the text size, replaced the last interface emoji with icons, added the layer/duration/segment tokens and the «Increase contrast» / «Reduce transparency» modes (the table «История перехода» in `styleguide.html` says what replaced what). `styleguide.html` is the reference: it reads the app's real CSS and `ICONS` and shows every token and component live, so **a new component gets a sample there**.

**Rules** (the audit enforces the first four and the durations as `css:` warnings, `check_css()` in `tools/audit.py`; a release should have none):
- **Colour lives only in tokens.** A literal colour (`#hex`, `rgb()`, `hsl()`) appears only in `:root{…}` and `:root[data-theme="dark"]{…}`; every rule uses `var(--role)`.
- **Every `var()` is defined** in `:root` (runtime exceptions set by JS: `--stick`, `--tabbar-h`, `--ts`).
- **No inline style carries a colour**, and inline styles at all are only for data: the `display:none` that JS toggles and the widths of progress bars (`width:${pct}%`, `left:${threshold}%`). A one-off margin in render code is a `.u-*` utility (`.u-mt0 .u-mtxs .u-mt1 .u-mt2 .u-mt3 .u-mb0 .u-mb1 .u-mb3 .u-mx0 .u-m0 .u-pt2 .u-pt3 .u-fs-sub .u-cursor-default`, `!important` like the inline style they replaced); anything else gets a class of its component.
- **Readable text follows the text size.** A `font-size` is `var(--fs-*)` or `calc(N * var(--ts))`; a size in px is only for the glyphs and the fixed chrome listed in `FIXED_FS` (`tools/audit.py`: the brand, the tab bar, the header buttons, the «A» samples, icon squares, round buttons, answer circles, placeholder emoji). The collapsed bar's title and back button grow up to 20 px (`min(var(--fs-body),20px)`), as in iOS. An icon in a line of text is sized with it (`1em` or `calc(N * var(--ts))`). A new fixed glyph goes into `FIXED_FS` on purpose, not by default.
- **Durations, layers and radii come from tokens** (`--dur`, `--dur-slow`, `--dur-tick`; `--z-*`; `--r-*`), never a literal `.2s` (the audit warns) or a new z-index layer.
- **Icons only from `ICONS`** (`ic(name, cls)` → `<svg class="sym">`, 1em, `currentColor`; 24 grid, 1.75 stroke, paths after Lucide/ISC; a value starting with `F:` is filled). A missing icon is drawn in the same style and added to the one-line JSON `ICONS`. **Emoji only as content**: owls 🦉, rank names, badge medals, promo icons from `DATA`, vitrina/prep items without a photo, the lesson-category emoji that `rowIco()` maps to icons. Since v1.120 the branch line of a promo (`pin`), the test time (`clock`), the mistakes review (`x`/`check`), the vitrina link chip (`cake`), the rank card stats (`flame`, `checklist`, `calendar`; the owl stays) and the week strip (`checklist`, `book`, `check`, `refresh`) use icons; the empty-favorites text puts `ic('star')` in place of the ☆ of its `ui` string. `ICONS` also holds a few reserve icons not used yet (`chevron-left/right`, `globe`, `medal`, `percent`, `gift`, `info`, `alert`, `thermo`, `gear`); the style guide shows them all.
- **Text in sentence case**: no upper-casing of badges or labels (`upperLocale()` stays only for a future case that really needs capitals).
- Don't write `font: … inherit` shorthands (`inherit` isn't allowed inside the shorthand and the whole declaration is dropped); buttons and inputs inherit the font through the reset.

**Tokens** (`:root`, dark values in `:root[data-theme="dark"]`; the app's dark theme is only the explicit toggle):
- *palette* (only for defining roles): `--n-0…--n-950` warm neutrals, `--caramel-300/500/600/700`;
- *backgrounds*: `--bg` (screen), `--bg-elevated` (groups, cards, answers), `--bg-tertiary`, `--bg-photo`;
- *text*: `--label`, `--label-2` (captions, values; AA), `--label-3`/`--label-4` (glyphs and empty states only);
- *fills and lines*: `--fill`, `--fill-2` (search, chips, segments, gray buttons), `--fill-3` (pressed row), `--separator` (0.5 px `--hair`);
- *the one accent*: `--tint` («can be tapped» / «selected», never decoration), `--tint-strong` (pressed, and text on `--tint-bg`), `--on-tint`, `--tint-bg`;
- *meaning*: `--red` (new, wrong), `--green` (running now, right, done), `--orange` (hot), `--blue` (cold), each with `-bg` (pale plate) and `-solid` (fill under `--on-solid` white text), `--gold-solid` (favorites/exam squares); light-theme `--red #b02f25`, `--green #236a41`, `--blue #285f84` keep AA even on their own pale plate over `--bg`;
- *materials*: `--material` (bars, with blur), `--glass`/`--on-glass` (buttons over photos), `--seg-thumb`, `--seg-thumb-shadow`, `--scrim`;
- *photos and solid fills* (same in both themes): `--on-solid`, `--photo-scrim`, `--on-photo-fill`, `--grabber-on-photo`, `--grabber-ring`;

- Every text/background pair is AA (4.5:1) in both themes; check a new pair before using it.

**Text styles** = the iOS ones: `.t-large` 34/41 bold · `.t-t1` 28/34 bold · `.t-t2` 22/28 bold · `.t-t3` 20/25 semibold · `.t-headline` 17/22 semibold · `.t-body` 17/22 · `.t-callout` 16/21 · `.t-sub` 15/20 · `.t-fn` 13/18 · `.t-c1` 12/16 · `.t-c2` 11/13. Nothing readable below 11 px; text inputs at least 16 px (iOS zooms in on smaller ones). **Dynamic Type**: «Ещё» → «Размер текста» steps through `TS_STEPS` (0.88 … 1.35), saved in `localStorage.sensum_textsize`, applied before first paint; as in iOS the tab bar labels, the brand and the header buttons stay fixed (see the rule above). Pinch zoom stays off (owner's decision). The system font only (SF Pro on iPhone); `.serif` only tightens the letter spacing.

**Layout and states**: every screen edge is `--gutter`; radii are concentric; small round buttons get an invisible `::after` hit area up to 44 pt; `[hidden]` always wins (`display:none!important` in the base), so JS can hide any block with the attribute (`.topblock` during a search). Pressed: buttons, chips and cards scale to `--press`, list rows highlight with `--fill-3`, text buttons fade; disabled = `--disabled`; `prefers-reduced-motion` switches every transition and animation off.

## Conventions worth knowing before editing recipe data

- **Espresso shots:** double shot = 18 g dose → 36 g yield (`["Эспрессо (двойной)","36 г"]`); single shot = 18 g output as half of a double pull (`["Эспрессо (одинарный)","18 г"]`, note "половина дабл-пролива" / AZ "dabl çəkimin yarısı").
- **Powder naming:** RU "Паудер <Name>" / AZ "<Name> paudəri" (e.g. "Паудер Elizabeta" / "Elizabeta paudəri").
- **Images:** `.card .ph{aspect-ratio:1/1}` and `.hero{aspect-ratio:16/10}`, both `object-fit:cover` — CSS crops at display time, so a new source photo doesn't need to be pre-cropped to a fixed ratio before adding it with `tools/photo.py`; a portrait photo can be center-cropped ~3:4 and a landscape one just resized, both read fine through `cover`.
- **Data source of truth:** never invent or guess a recipe change — it always comes from the project owner's explicit instruction (text, voice note, or photo of a handwritten recipe).
